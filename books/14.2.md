### 14.2 A Shift in Focus: Not Training the Model — Versioning the Prompt

Since the model in LLMOps is already fixed and doesn't change, the one lever an AI engineer actually pulls day to day is **the prompt** — exactly how the request to the model is worded. And versioning that lever turns out to matter just as much as versioning code.

If a prompt is hardcoded directly into the codebase, even a minor wording change requires a **full development cycle** — code review, tests, build, deploy. That's slow: fixing one phrase means waiting for an entire release. It's also risky — if a new wording made responses worse, figuring out exactly _when_ and _because of what change_ becomes much harder if the prompt isn't tracked as its own versioned entity.

Versioning solves both problems at once:

- **Fast rollback.** If a new prompt version starts producing weaker answers, you can revert to the previous version without touching the rest of the code or waiting for a release.
- **A history of experiments.** You can see which wordings were tried before, what worked, and what didn't — instead of relying on memory or a chat log.
- **Decoupling the release cycle from experimentation.** Whoever is tuning the wording (not necessarily a developer) can test variations without waiting on a full backend deploy.
