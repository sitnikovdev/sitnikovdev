## 14.1 The Problem: How Managing an LLM System Differs from Managing a Regular ML Model

In classical ML, the main task is **building a model and training it from scratch.** That requires deep theoretical grounding: an ML engineer researches how training actually behaves — tracking things like **vanishing and exploding gradients**, where gradients in a deep network either shrink toward zero or grow uncontrollably, breaking training. This is research in the purest sense — work happening at the level of the model's own math.

**LLMOps is different.** An AI engineer almost never trains a model from scratch. They get a model that's already trained and ready — via an API or self-hosted — and take on a completely different job: **making sure the model gives useful, adequate answers to user questions, and that answer quality doesn't degrade over time.**

That job breaks down into a few concrete responsibilities:

- **Evaluation** — regularly running the model against test datasets to catch regressions quickly, if a new prompt or model version starts answering worse
- **Security** — defending against prompt injection and other ways someone might push the model to behave outside its intended bounds
- **Cost** — watching for cases where the system is overpaying for an expensive model when a cheaper one would do the job

> ML engineers are responsible for making the model learn. AI engineers are responsible for making sure the model doesn't un-learn — in the broad sense: no quality degradation, no new vulnerabilities, no runaway cost.
